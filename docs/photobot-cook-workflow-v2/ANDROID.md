# Android: состав смены и повар фотографии

**Версия:** PHOTOBOT_COOK_WORKFLOW_V2_20261105. Канонический контракт — DATA_CONTRACT.md в backend-репозитории. Это спецификация, приложение ещё не изменено.

## 1. Назначение и границы

Расширить приложение «Фото в чистоту»: один раз за день после 11:00 подтвердить поваров и операторов, выбрать основного повара, показывать плашки работающих поваров. Выбор дополнительного повара действует на **один успешно сохранённый снимок**, затем приложение возвращается к основному. Продукцию фотографируют после открытия. Режим серии не добавлять.

Обычная съёмка основного повара сохраняет одно действие — нажатие Bluetooth-кнопки или экранного затвора. Полноэкранный просмотр камеры, отправка, история и повторные загрузки продолжают работать.

Авторство относится к фотографии, поскольку номера заказа в действующем протоколе нет. Выбранный оператор означает заявленного сотрудника смены; это не доказательство, кто физически нажал затвор. Личные MAX-аккаунты сотрудников не требуются. Категории, продукты, причины нарушений и видеоуроки обслуживает backend/MAX; второй каталог проверки внутри APK не создавать.

Аудируемая версия Android: **3d457a57b8bfd769c574aa8fda8be7221c9910a7**. Перед реализацией сверить более новый HEAD, сохраняя последующие изменения.

## 3. Ежедневное подтверждение

Состояние подтверждения хранить по филиалу и операционному дню в часовом поясе филиала. После 11:00 при первом открытии показывать одну форму: повара, операторы, основной повар. Разрешить несколько сотрудников каждой роли. Количество людей вычислять из выбора; не вводить независимый счётчик, способный расходиться со списком.

Подтверждённый состав сохраняется локально и переживает закрытие приложения. Повторный запуск в тот же день и возврат из истории не требуют повторного заполнения. На новый день вчерашние сотрудники служат подсказкой, но вчерашнее подтверждение недействительно.

Проверять день в onResume и перед съёмкой: телефон может оставаться открытым через 11:00. Для появления формы на открытом экране допустима проверка времени только пока Activity активна. Фоновое пробуждение закрытого приложения и новые MAX-таймеры не нужны. Восстановление старой очереди не зависит от заполнения сегодняшней формы.

До подтверждения нельзя молча подписывать новые снимки вчерашним поваром. Если общий сценарий допускает снимок без определённого автора, сохранять явное неизвестное авторство. Недоступность сети не должна заставлять выдумывать сотрудника: использовать локальный справочник либо ручное добавление.

## 4. Нижняя панель и разовый выбор

Показать подпись «Следующее фото: Фамилия Имя» и плашки поваров подтверждённой смены. Основной выделен постоянно; при разовом выборе другого сотрудника ясно показать, что именно **следующий снимок** будет его. Цвет дополнить текстом/индикатором, чтобы состояния различались без распознавания цвета.

Последовательность:

1. Пользователь выбирает дополнительного повара.
2. При принятии команды затвора приложение резервирует выбор за конкретной попыткой съёмки.
3. До CameraX фиксируются автор, смена/revision, филиал и время.
4. После onImageSaved фотография и её метаданные сохраняются в Room с признаком очереди.
5. После успешной локальной записи панель возвращается к основному; отправка продолжается независимо.

Сброс после ответа сервера или доставки MAX запрещён: при задержке сети разовый выбор иначе затронет несколько кадров. Ошибка камеры или записи не расходует выбор незаметно; пользователь видит ошибку и может повторить попытку.

Нужен короткий guard локальной съёмки либо атомарная резервация разового выбора. Текущий inProcess защищает старую processQueue, а не камеру; onKeyDown не отсекает повтор клавиши. Два быстрых события не должны назначить разового повара двум снимкам. Следующую съёмку не блокировать ожиданием сети. Незавершённый разовый выбор после перезапуска не восстанавливать как постоянный.

## 5. Контракт метаданных фотографии

Передавать новый JSON photoContext по DATA_CONTRACT.md как необязательное расширение multipart, сохранив photo/deviceUuid/clientUploadId. clientUploadId остаётся внешним полем, не дублируется внутри JSON; ключ идемпотентности — пара (deviceUuid, clientUploadId), как в действующем backend. Следующие имена согласованы с контрактом V2; любые уточнения синхронно вносить в оба репозитория.

| Данные | Требование |
|---|---|
| schemaVersion | 1, версия photoContext |
| clientUploadId | Существующий устойчивый UUID фотографии; не генерировать заново при повторе |
| capturedAt, timezone | Время принятия команды съёмки на устройстве; серверные времена хранить отдельно |
| branchRef / bindingRevision | Ссылка на действующую привязку филиала, не выдуманный новый фактический ID |
| shiftRef, shiftRevision | Стабильная ссылка на подтверждённый состав и его версию |
| cookRef, cookNameSnapshot | Идентификатор выбранного повара и отображаемое имя на момент съёмки |
| selectionSource | main_default / one_shot / explicit_unknown / shared |
| rosterConfirmedAt | Время подтверждения состава, не время отправки |

Состав операторов хранится в снимке смены; его не подменять полем автора продукции. Время устройства не объявлять доказанным временем приготовления.

Для offline-новичка допустим локально созданный устойчивый временный идентификатор, явно помеченный как временный и ограниченный филиалом/устройством. Не подставлять фиктивный серверный employee_id. Backend должен сохранять ссылку до разрешения личности; совпадение ФИО не даёт права автоматически объединять людей.

## 6. Очередь, изменения смены и совместимость

Метаданные записываются вместе с фотографией и читаются **из её записи** обоими отправителями. Повтор загрузки, новый день, изменение основного повара и перезапуск не переписывают автора ожидающих кадров. PhotoHistoryStore.addQueued при существующем пути сохраняет первоначальную атрибуцию.

Сегодня capturedAt создаётся внутри addQueued после сохранения файла. Новая реализация передаёт заранее зафиксированное время вместо повторного вычисления при отправке.

Смена состава создаёт новую revision и действует на будущие снимки. Уход основного требует явного выбора нового. При смене филиала сбросить подтверждение/разовый выбор; прежнюю очередь не переносить к новому филиалу. При изменении смены во время съёмки завершить кадр с зарезервированным снимком данных. Поздняя синхронизация не должна задним числом назначать автора; разрешение временного ID сохраняет исходный выбор, а исправление автора требует отдельного явного действия с историей.

Backend сначала начинает принимать и сохранять расширение; старые APK продолжают работать без новых полей. Новое приложение должно получать capability и явное подтверждение сохранения photoContext, чтобы плашка не создавала ложную уверенность при сервере, игнорирующем метаданные. Изображение, уже принятое без acknowledgement, не пересылать с новым clientUploadId: контекст сохраняется локально и досинхронизируется идемпотентно без второго MAX-фото. При повторном clientUploadId противоречащий автор не перезаписывается молча. Фото и подтверждение смены должны обрабатываться независимо от порядка доставки.

Существующий QueuedPhotoMaintenance удаляет прошлые дни по lastModified. Не обещать многодневную offline-доставку и не менять срок хранения попутно; это отдельная политика.

## 7. Миграция и проверки

Добавление полей требует **сохраняющей миграции Room 1→2**. Не использовать destructive fallback для обновления: очередь, UUID, история и миниатюры должны остаться. Новые поля старых записей получают неизвестные значения; текущий основной повар в них не подставляется. Общий MainActivity используется обоими flavor, поэтому поведение legacy проверить отдельно.

Обязательные проверки:

- Один повар: подтверждение дня и обычная Bluetooth-съёмка без дополнительных нажатий.
- Экран открыт через 11:00; повторный вход того же дня; новый день.
- Второй повар на один снимок, затем основной, включая медленную сеть.
- Ошибка камеры/Room, повтор клавиши, два быстрых нажатия.
- Перезапуск и смена состава/филиала при непустой очереди.
- Одинаковые сохранённые метаданные foreground service и worker.
- Offline-новичок, разрешение временного ID без смены автора.
- Обновление с реальной Room version=1 без потери данных.
- Старый APK с новым backend; отсутствие ложной атрибуции у старых фото.
